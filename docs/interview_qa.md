# Day 7 模拟面试：8 个 RAG 追问答案草稿

> 用途：面试前 30 分钟翻一遍，确保每个答案能闭卷口述 1-2 分钟。
> 回答策略：先给结论，再讲原理，最后结合自己的项目经验举例。

---

## Q1：chunk_size 为什么选 512？

**结论**：我在 9 组配置里做过对比实验，最终选了 `recursive_512_0`（chunk_size=512，overlap=0）。

**为什么是 512**：
- 太小（如 128）会把一个完整概念切碎，比如"MDP 五元组定义"被切成两半，检索时只能命中一半；
- 太大（如 2048）会让一个 chunk 混入多个话题，检索时的向量是"平均语义"，反而不精准；
- 512 是中文长文本的常见折中值，一个完整定义 + 一个例子刚好放得下。

**为什么 overlap 选 0**：
- 我在 Day 4 的对比实验里发现，`fixed_512_50`（overlap=50）的 MRR 反而比 `fixed_512_0` 低（0.2250 vs 0.2667）。
- 原因是重叠片段引入了冗余，检索时稀释了真正相关片段的得分。

**最终数据**：`recursive_512_0` 的 MRR 0.30 是所有 9 组里最高的。这不是拍脑袋选的，是实验数据支撑的。

## Q2：纯向量够用吗？

**结论**：不够。在中文专有名词密集的语料上，纯向量会输给 BM25。

**为什么不够**：
- 向量擅长"语义改写"匹配，比如"什么是 MDP"能匹配到"MDP 定义"；
- 但对精确关键词（人名、术语、编号、公式符号）不敏感。比如"马尔可夫决策过程"这五个字，BM25 能精确命中，向量可能因为语义相近而被其他"决策过程"类的内容挤占。

**我的实测数据**：
- 纯向量：Recall@5 = 0.80，MRR = 0.80
- 纯 BM25：Recall@5 = 0.85，MRR = 0.85
- 在这个语料上，**纯 BM25 反而比纯向量高 5 个百分点**。

**结论**：向量不是万能的，用不用要看语料特性。工业界通常用混合检索补齐各自的短板。

---

## Q3：BM25 和向量检索各自适合什么？

**BM25 适合**：
- 专有名词、术语、代码、编号、公式符号
- 短查询（用户就问一个词）
- 语料里关键词区分度高的场景

**向量检索适合**：
- 语义改写（同义替换、句式变换）
- 长文本查询（用户问一段话）
- 语料表达多样、同义词多的场景

**我的项目举例**：
- 问题"γ 代表什么"→ BM25 精确命中 γ 所在片段
- 问题"折扣因子的作用"→ 向量能匹配到"γ ∈ [0,1] 是对未来奖励的折扣因子"，即使问题里没出现 γ

**加分点**：可以补充"混合检索 + RRF"是工业界主流做法，但如果语料小、关键词特征强，单路 BM25 有时已经够用，别为了复杂而复杂。

## Q4：RRF 为什么有效？

**RRF（Reciprocal Rank Fusion）**：不关心两个检索器的原始分数，只看排名。

**公式**：每个候选的融合分 = Σ 1/(k + rank)，k 通常取 60（我调参时试过 k=10 效果更好）。

**为什么有效**：
- 不同检索器的原始分数**不可比**：BM25 可能给出 30 分，向量给出 0.8 分，直接加权求和没意义；
- 但**排名是可比的**：无论哪个检索器，"排第 1"都是排第 1；
- RRF 只看排名，就绕开了"分数不可比"这个坑。

**为什么 k 要取中间值**：
- k 太大（如 60）：排名第 1 和第 10 的分差被拉平，噪声容易挤上来；
- k 太小（如 1）：排名第 1 就是 0.5 分，太极端；
- k=10~60 之间是常见范围，我的实验中 k=10 效果最好。

**我的实测**：
- 默认参数（k=60，权重1.0:1.0）：MRR = 0.8167
- 调参后（k=10，权重1.0:0.5）：MRR = 0.8250
- 但依然没超过纯 BM25（0.85），说明本语料上混合检索的增益有限。

## Q5：你怎么评估检索质量？

**两层评估**：

**第一层：自动指标**
- **Recall@K**：top-K 里有没有包含正确答案所在的 chunk
- **MRR（Mean Reciprocal Rank）**：正确 chunk 的平均倒数排名，越靠前越高
- 我在 Day 4 用这两指标跑了 9 组切分对比，Day 5 用来对比 BM25/向量/混合

**第二层：人工抽样**
- 随机抽 10 条 query，肉眼看 top-3 chunk 里有多少是真正相关的
- 特别是看 top-1 是否精准，因为 LLM 的答案质量主要被 top-1 主导

**第三层：端到端评估（RAGAS）**
- Context Precision 和 Context Recall 是 RAGAS 里直接评估检索质量的两个指标
- Precision 看"有用的排得靠不靠前"，Recall 看"该找的有没有找全"

**加分点**：能说出"检索评估和生成评估要分开做"，因为检索好不代表生成好，生成差也不一定是检索的锅。

---

## Q6：检索失败怎么排查？

**按顺序排查 4 层**：

**第 1 层：Embedding 一致性**
- 入库和查询是不是用了同一个模型？这是最常见的坑。
- 我 Day 6 就踩过：ChromaDB 默认会下载一个英文模型 `all-MiniLM-L6-v2`，如果不显式指定 `embedding_function=None`，就会用中文查询去匹配英文索引，检索全废。

**第 2 层：top-k 数量**
- 太小（如 top-1）：一个噪声片段就毁掉结果
- 太大（如 top-50）：LLM 的 context 被稀释，关键片段被淹没
- 我的项目用 top-3 到 top-5 比较合适

**第 3 层：chunk 切分**
- chunk 太大：一个 chunk 混了多话题，向量不精准
- chunk 太小：一个概念被切碎，跨 chunk 无法被召回
- 我的项目从 9 组配置里选出 `recursive_512_0`

**第 4 层：检索算法本身**
- 关键词密集的语料 → 优先 BM25
- 语义改写密集的语料 → 优先向量
- 两者都重要 → 混合检索

**加分点**：能具体举出自己项目里"Q5 检索漏召、Q4 数学字体导致评估误判"的真实 Badcase。

## Q7：RAGAS 三个指标分别代表什么？

**Faithfulness（忠实度）**：
- 答案里的每个论断，是不是都能在检索到的 context 里找到依据？
- 低分意味着模型在**幻觉**。
- 我的项目平均 0.8683，最低一条 0.33（那条检索完全失败）。

**Context Precision（上下文精确率）**：
- 检索出来的片段里，有用的内容是不是排在前面？
- 低分意味着**噪声片段占了 top-k**。
- 我的项目平均 0.90，只有 Q5 出现 0 分。

**Context Recall（上下文召回率）**：
- 该找出来的资料，有没有被检索到？
- 低分意味着**漏召**——PDF 里明明有答案，但检索没找到。
- 我的项目平均 1.0，说明向量检索在这个小语料上已经召回了所有必要内容。

**排查顺序**：
- Faithfulness 低 → 查 Prompt、查幻觉，不是检索问题
- Precision 低 → 查 top-k 排序、查切分粒度
- Recall 低 → 查 Embedding、查 chunk 大小、查是否需要混合检索

## Q8：这个项目相比普通 RAG 的差异化在哪？

**差异化 1：完整闭环**
- 普通 RAG 教程：跑通"PDF → 答案"就结束。
- 我的项目：PDF → 答案 → RAGAS 评估 → Badcase 归因 → 改进方向，闭环完整。

**差异化 2：可量化**
- 9 组切分对比（含 MRR 数据）
- 3 种检索方案对比（BM25 / 向量 / 混合）
- RAGAS 三指标（Faithfulness 0.87 / Precision 0.90 / Recall 1.00）
- ≥5 条 Badcase 归因表
- 不是"我感觉它能用"，是"数据证明它哪里好、哪里差"。

**差异化 3：工程化**
- Docker 打包，一键复现
- FastAPI 服务化，`/upload` + `/ask` 接口
- Agent 工具化，`search_pdf` 可被 LLM 自主调用
- 完整 README + 目录分层

**差异化 4：真实踩坑经验**
- ChromaDB 默认下模型导致卡死 → `embedding_function=None` 解决
- RAGAS 0.4.3 与 langchain-community 0.4.x 版本冲突 → `sys.modules` 占位解决
- Docker build 遇 Python 3.14 兼容问题 → 逐层排查

**差异化 5：有"反直觉"的诚实结论**
- 加了 Rerank 指标没提升？因为我发现 Recall 已经饱和，Rerank 无增益空间。
- 这比"我加了 Rerank 提升 10%"更可信，面试官会更认可这种实验精神。

**一句话总结**：不只是"做了个 RAG"，而是"做过、评过、踩过坑、能讲清楚为什么这么做"。
