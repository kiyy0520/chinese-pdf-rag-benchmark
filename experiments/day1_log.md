# Day 1 实验日志：评估基准 + 文档解析管道

## 1. 实验目标
完成文档解析管道的搭建，产出一份干净的语料文本，并建立一套可量化的 Golden QA 评估基准。

## 2. 数据准备
- **原始语料**：`data/raw/sjtu_rl_lecture.pdf`（上海交通大学《强化学习》课件）
- **Golden QA**：`data/golden_qa/qa.json`，共 20 条。
  - Easy: 8 条，Medium: 8 条，Hard: 4 条。

## 3. 解析实验结果
- **解析工具**：PyPDFLoader (基于 pypdf)
- **原始字符数**：6574
- **清洗后字符数**：6473
- **字符变化率**：1.54% （满足 < 5% 的验收要求）
- **清洗逻辑**：去除空行和纯数字页码。
- **输出文件**：`data/processed/day1_pdf_text.txt`

## 4. 技术决策记录
1. **开发环境决策**：选择 VSCode + `.venv` 虚拟环境，而不是全局 Python 或 PyCharm。
   - *理由*：VSCode 轻量且终端集成度高；虚拟环境可以防止污染全局库，方便后续工程化打包与依赖管理。
2. **PDF 解析器决策**：选用 `PyPDFLoader` 而不是 `pdfplumber` 或 `PyMuPDF`。
   - *理由*：PyPDFLoader 是 LangChain 生态的标准组件，后续做 RAG 检索时更容易与 LangChain 的文档加载机制无缝对接。
3. **去页眉页脚策略决策**：采用“按行过滤空行和纯数字行”的简单规则，而不是复杂的正则匹配或字体大小分析。
   - *理由*：Day 1 的目标是“基础去页眉页脚”，当前 PDF 结构简单，简单规则能达到 98.46% 的保留率，过度设计反而耗时且收益不大。
4. **Golden QA 生成策略**：基于 PDF 原始文本人工提取，并保持 `source_context` 与原文逐字一致。
   - *理由*：作为后续评估 RAG 系统的黄金基准，必须确保 `ground_truth` 能在原文中找到绝对支撑，否则评估结果不可信。
5. **分步推进策略**：Day 1 先将所有目录和基础管道拉通，暂不引入复杂清洗和检索算法。
   - *理由*：遵循“先跑通，再优化”的工程原则，避免一开始陷入细节泥潭，确保每天都有可量化、可交付的产出。
