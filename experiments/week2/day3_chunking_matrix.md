# Day 3：文本切分策略实验报告

## 1. 实验目的
对比固定长度切分、递归字符切分、Markdown标题+递归切分在不同 `chunk_size` 和 `overlap` 下的表现，并记录切分失败案例。

## 2. 实验环境与样本
- 样本文件：`data/day3_sample.md`
- 包含内容：普通段落、代码块、Markdown 表格、问答对
- 策略：fixed, recursive, markdown_recursive
- 参数矩阵：chunk_size = [512, 1024, 2048], overlap = [0, 50, 100]

## 4. 切分失败案例记录

### 案例1：切断表格
- **配置**：`fixed_512_0`，以及 `fixed` 小尺寸强制触发
- **现象**：表格的头部和身体被硬生生切到了两个不同的 chunk 中。
- **具体证据**：Chunk 3 结尾是 `| 张三 |`，Chunk 4 开头是 `25   | 北京 |`。
- **影响**：检索时只能命中一半表格，模型无法回答完整信息。
- **修复建议**：使用 `markdown_recursive` 或带 `\n\n` 优先的递归切分。

### 案例2：切断代码块
- **配置**：`fixed` 极小尺寸（如 `chunk_size=50`）强制触发
- **现象**：代码块在中间被硬切断。
- **具体证据**：第 1 块结尾是 `这是一个简`，第 2 块开头是 `单的加法函数`；第 2 块结尾是 `return resul`，第 3 块开头是 `t\nprint(...)`。
- **影响**：代码语法破坏，模型无法正确理解和补全代码。
- **修复建议**：使用专门的代码切分器，或增大 `chunk_size`，或优先按 `\n\n` 切分。

### 案例3：切断问答对
- **配置**：`fixed` 极小尺寸（如 `chunk_size=30`）强制触发
- **现象**：`Q:` 和 `A:` 被分割到两个不同的 chunk。
- **具体证据**：第 1 块结尾是 `...小块（c`，第 2 块开头是 `hunk）的过程。`；第 2 块结尾是 `...overlap？\n`，第 3 块开头是 `A: overlap 是为了...`。
- **影响**：检索到问题但找不到答案，或反之。
- **修复建议**：使用零宽断言 `(?=Q:)` 在 Q 前面切分，保证 Q 和 A 在同一个 chunk。

## 5. 结论与建议
- 对于 Markdown 文档：优先使用 `markdown_recursive`，保证章节完整性。
- 对于普通文本：`recursive` 表现最均衡。
- 避免使用 `fixed` 处理结构化内容。
- 参数建议：512/50 适用于大多数 RAG 场景。

### 6.2 数据分析与结论

1. **固定长度切分**：最大长度严格等于 `chunk_size`，因为它是“一刀切”策略。当 `overlap` 增加时，最小长度也会变大（因为重叠部分保住了更多上下文），但这也导致冗余增加，chunk 数量可能变多。`fixed_512_0` 的 `min_len=137` 说明它切出了极短的碎片。
2. **递归字符切分**：最大长度通常**小于** `chunk_size`（例如 `recursive_512_0` 最大长度只有 488），因为它在段落或句子边界处提前切分了。`min_len=330` 比固定切分更健康，说明它极少切出“残渣碎片”。
3. **Markdown + 递归切分**：表现最稳定。由于先按标题切分，每个章节自成一体，再配合递归切分，`min_len` 普遍在 200 以上，说明结构化边界得到了很好的保护。
4. **参数建议**：
   - 如果文档是 Markdown，首选 `markdown_recursive`，配 `512/50` 或 `1024/50`。
   - 如果是纯文本，用 `recursive`，配 `512/50`（平衡性好）或 `1024/100`（上下文更完整）。
   - 尽量**不要用 `fixed` 处理结构化文档**，因为 `fixed_512_0` 已经证明了它会切出 137 字符的碎片。
