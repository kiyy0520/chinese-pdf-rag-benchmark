# Day 4 切分策略评估指标说明

## 一、指标字典

| 字段名 | 中文含义 | 解读方式 |
| :--- | :--- | :--- |
| `config_name` | 切分策略名 | 命名规则：`策略_切块大小_重叠大小`。如 `recursive_512_0` 代表：递归切分、块大小 512 字符、无重叠。 |
| `recall@5` | 前5个结果命中率 | 系统“找不找得到”的及格线。20 道题中 `0.3` 代表有 6 道题在检索出的前 5 个文本块里包含了正确答案。 |
| `mrr` | 正确答案排名质量 | 系统“准不准”的评分。排第 1 = 1.0 分，排第 2 = 0.5 分，排第 3 = 0.33 分。`0.3` 意味着平均下来，正确答案大概排在第 3 名左右。 |
| `avg_latency_ms` | 检索平均耗时 | 每次提问后，系统“找资料”花了几毫秒。数字越小，用户体验越爽。 |
| `total_chunks_evaluated` | 参与评估题目数 | 本次实验为固定的 20 道 Golden QA。 |

**选型逻辑：**
1. 第一原则（Recall@5）：`recursive_512_0` 与 `fixed_1024_0` 打平（均为 0.3）。
2. 第二原则（MRR）：`recursive_512_0`（0.3）> `fixed_1024_0`（0.275），说明递归切分的排序更靠前。
3. 第三原则（延迟）：延迟差异仅 0.3ms，人类完全无感知，牺牲无感延迟换取排序质量是划算的。

**最终结论：**
选 `recursive_512_0`（递归切分、块大小512、无重叠）作为当前业务场景下的最优切分配置。

**工程反思（进阶）：**
整体 Recall@5 只有 0.3，瓶颈不在切分，而在于“PDF中的数学公式被解析成了乱码（下划线、花括号丢失）”，向量模型处理此类符号天生吃亏。下一阶段优化方向应该是：数学公式的单独解析与清洗。
