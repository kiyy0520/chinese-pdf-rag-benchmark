# 中文强化学习 PDF RAG 系统：完整实验报告

> 项目周期：Day 1 - Day 7
> 语料：两篇中文强化学习课件（`2-马尔可夫决策过程.pdf`、`sjtju_rl_lecture.pdf`）
> 目标：构建可复现、可评估、可交付的 RAG 问答系统，并通过实验数据给出选型依据

---

## 一、项目概述

本项目以中文强化学习教材为语料，构建了一套完整的 RAG（Retrieval-Augmented Generation）流水线，覆盖 **PDF 解析 → 文本清洗 → 切分 → 向量化 → 检索 → Prompt → LLM 生成 → API 服务化 → RAGAS 评估 → Badcase 归因** 全链路。

系统同时提供：
- **FastAPI 服务**：`/upload` 上传 PDF，`/ask` 提问
- **Agent 工具**：`search_pdf` 可被 LLM 自主调用
- **Docker 镜像**：一键复现环境
- **完整实验记录**：9 组切分对比、3 种检索方案、RAGAS 三指标、5 条以上 Badcase 归因

---

## 二、数据集与评估基准

### 2.1 语料概况

| 文件 | 内容 | 页数 |
|---|---|---|
| `2-马尔可夫决策过程.pdf` | MDP 定义、五元组、值迭代、策略迭代 | 约 30 页 |
| `sjtju_rl_lecture.pdf` | 强化学习基础、占用度量、值函数 | 约 50 页 |

### 2.2 Golden QA 构建

人工从课件中整理 **20 条 Golden QA**（`data/golden_qa/qa.json`），每条包含：
- `question`：自然语言问题
- `ground_truth`：标准答案
- `source_context`：原文出处片段
- `difficulty`：easy / medium

难度分布：easy 15 条，medium 5 条。

## 三、实验一：切分策略对比

### 3.1 实验设计

在 `recursive` 与 `markdown_recursive` 两大类切分器下，测试 9 组 `chunk_size × overlap` 组合。评估指标：
- **Recall@5**：top-5 检索结果中包含正确答案的比例
- **MRR**：正确结果的平均倒数排名

### 3.2 对比表

| 配置 | Recall@5 | MRR | 平均延迟(ms) | chunk 数 |
|---|---|---|---|---|
| fixed_512_0 | 0.30 | 0.2667 | 9.05 | 20 |
| fixed_512_50 | 0.25 | 0.2250 | 2.58 | 20 |
| fixed_1024_0 | 0.30 | 0.2750 | 2.58 | 20 |
| markdown_recursive_512_0 | 0.30 | 0.2292 | 2.65 | 20 |
| markdown_recursive_512_100 | 0.25 | 0.2167 | 2.82 | 20 |
| markdown_recursive_1024_0 | 0.30 | 0.2417 | 2.90 | 20 |
| markdown_recursive_1024_50 | 0.25 | 0.2500 | 2.92 | 20 |
| markdown_recursive_2048_0 | 0.30 | 0.2500 | 2.95 | 20 |
| **recursive_512_0** | **0.30** | **0.3000** | 2.88 | 20 |

### 3.3 结论

1. **`recursive_512_0` 综合最优**：Recall@5 与最高分并列，但 **MRR 明显领先**（0.30 vs 0.25~0.275），说明正确片段排名更靠前。
2. **overlap 并非越大越好**：`fixed_512_50`、`markdown_recursive_512_100` 反而 MRR 下降，原因是重叠片段引入了冗余，稀释了真正的相关片段。
3. **chunk_size 512 优于 1024**：1024 的 chunk 会混入多个话题，检索时命中精度下降。
4. **最终选型**：`recursive_512_0`，作为后续所有实验的基础切分配置。

## 四、实验二：检索方案对比

### 4.1 实验设计

在 `recursive_512_0` 切分下，对比三种检索方案：

1. **纯向量**：BGE-large-zh-v1.5 + ChromaDB 余弦检索
2. **纯 BM25**：`rank-bm25` 库，jieba 分词
3. **混合检索**：BM25 + 向量，RRF 融合（k=10，权重 1.0:0.5）

### 4.2 对比表

| 方案 | Recall@5 | MRR | 备注 |
|---|---|---|---|
| 纯向量 | 0.8000 | 0.8000 | 语义理解强，对排版/公式匹配弱 |
| **纯 BM25** | **0.8500** | **0.8500** | 专业术语命中率极高，当前语料的最优单路方案 |
| 混合检索（k=10，权重1.0:0.5） | 0.8500 | 0.8250 | 调参后 MRR 从 0.8167 提升至 0.8250，但仍未超越纯 BM25 |

### 4.3 结论

1. **纯 BM25 在本语料上表现最优**：因为问题里包含大量专业术语（"马尔可夫决策过程"、"占用度量"、"值迭代"），关键词匹配比语义匹配更精准。
2. **混合检索并非稳赢**：在"单路强命中，另一路全未命中"的问题上，RRF 融合会因为另一路的噪音文档导致正确文档排名下降。
3. **调参有效但有限**：将 RRF 的 `k` 从 60 降到 10，向量权重从 1.0 降到 0.5 后，MRR 从 0.8167 提升至 0.8250，但依然无法超越纯 BM25。
4. **最终选型**：本语料场景下，**纯 BM25 是最优单路方案**。混合检索作为可选策略保留。

## 五、实验三：生成质量 RAGAS 评估

### 5.1 实验设计

用 10 条端到端问题（从 20 条 Golden QA 中精选），跑完整 RAG 链路后，用 RAGAS 0.4.3 计算三个指标：

- **Faithfulness**：答案对检索内容的忠实度
- **Context Precision**：检索片段中相关内容的排序质量
- **Context Recall**：检索是否召回了所有必要内容

裁判 LLM：Qwen-Plus，temperature=0。

### 5.2 逐题结果表

| 序号 | 问题 | Faithfulness | Context Precision | Context Recall |
|---|---|---|---|---|
| 1 | 什么是随机过程？ | 1.00 | 1.00 | 1.00 |
| 2 | 什么是马尔可夫过程？ | 1.00 | 1.00 | 1.00 |
| 3 | MDP 五元组表示？ | 1.00 | 1.00 | 1.00 |
| 4 | γ 代表什么？ | 1.00 | 1.00 | 1.00 |
| 5 | 强化学习与监督/无监督学习区别？ | **0.33** | **0.00** | 1.00 |
| 6 | 什么是占用度量？ | **0.60** | 1.00 | 1.00 |
| 7 | 价值函数 V^π(s) 的定义？ | 1.00 | 1.00 | 1.00 |
| 8 | 描述 MDP 动态过程 | 1.00 | 1.00 | 1.00 |
| 9 | 价值函数的 Bellman 等式？ | **0.75** | 1.00 | 1.00 |
| 10 | 价值迭代的过程？ | 1.00 | 1.00 | 1.00 |
| **平均** | — | **0.8683** | **0.9000** | **1.0000** |

### 5.3 结论

1. **Context Recall 满分 1.0**：说明向量检索在这个小规模语料上**已经把所有必要资料都召回了**，这是后续 Rerank 无增益的根本原因。
2. **Context Precision 0.9**：检索排序基本合理，只有第 5 题出现 0 分（检索到完全不相关的片段）。
3. **Faithfulness 0.8683**：3 条问题低于 1.0，主要原因是 LLM 对公式/概念做了**自主扩展解释**。
4. **最大问题在第 5 题**：检索完全没命中相关片段，导致答案"根据提供的资料无法回答"，同时 Precision=0。

## 六、实验四：Rerank 增益验证（挑战性实验）

### 6.1 实验设计

在原有纯向量检索（top-3）基础上，引入 **BAAI/bge-reranker-large** 进行二次排序：
- 方案 A：向量检索 top-3 → LLM
- 方案 B：向量召回 top-10 → Rerank → 取 top-3 → LLM

两方案跑同一批 10 个问题，对比 RAGAS 三指标。

### 6.2 对比表

| 指标 | 纯向量 | 向量+Rerank | 变化 |
|---|---|---|---|
| Faithfulness | 0.8883 | 0.8657 | **-0.023** ↓ |
| Context Precision | 0.9000 | 0.9000 | 持平 |
| Context Recall | 1.0000 | 1.0000 | 持平 |

### 6.3 结论

1. **Rerank 在本语料上没有带来提升，Faithfulness 略降**。这不是代码 bug，而是**真实场景里的常见现象**。
2. **根本原因**：Context Recall 已饱和（1.0），说明向量检索已经把该找的资料全找出来了。Rerank 只能对已有候选重排序，**没有召回增益空间**。
3. **Precision 无变化**：说明原 top-3 本来就已经是相关片段，重排后顺序变化不大。
4. **Faithfulness 略降**：Rerank 换了几个片段，新片段的长度和上下文略有差异，导致 LLM 引用时略微不同，属于**随机波动**。
5. **面试加分点**：能说出"**我加了 Rerank，指标没提升，因为数据集规模小、Recall 已饱和**"——这比"我加了 Rerank 提升了 10%"更可信、更有实验精神。

## 七、Badcase 归因（≥5 条）

| 编号 | 问题 | 类型 | 具体原因 |
|---|---|---|---|
| **Q4** | MDP 五元组中 γ 代表什么？ | 漏召/符号歧义 | 数学字体 `γ` 与 `𝛾` 在文本匹配时编码不同，导致评估器误判为漏召 |
| **Q5** | 强化学习与监督/无监督学习区别？ | 误召/融合挤占 | 向量排第 0、BM25 排第 1。调参后混合排第 2，说明降低 k 值和向量权重能缓解噪音挤占 |
| **Q18** | 引入折扣因子 γ 的目的是什么？ | 长距离依赖 | 正确文本块中"折扣因子"与"金融例子"相距较远，且受 γ 字体不一致影响，未被完整匹配 |
| **Q20** | 不知道环境动态时有哪两种解决思路？ | 语义歧义 | 问题用词是"不知道"，但文档用词是"不是明确给出的"，语义匹配存在鸿沟 |
| **Q3** | MDP 五元组表示？ | 评估器污染 | 初版评估因 `source_context` 包含五元组公式而漏判，修正评估器后命中，可作为"评估器污染"典型案例 |
| **Q6（Day6）** | 什么是占用度量？ | 轻度幻觉 | LLM 给出公式后又补充"即：…期望访问频次"，原文无此表述，属于自主扩展 |
| **Q9（Day6）** | 价值函数的 Bellman 等式？ | 过度解释 | LLM 逐项解释公式变量含义，原文未逐条列出，属于自主扩展 |

### 归因分类总结

| 类别 | 数量 | 典型问题 |
|---|---|---|
| 检索漏召 | 2 | Q4、Q18 |
| 融合噪音挤占 | 1 | Q5 |
| 语义歧义 | 1 | Q20 |
| 评估器污染 | 1 | Q3 |
| LLM 幻觉/过度解释 | 2 | Q6、Q9 |

## 八、改进方向

### 8.1 短期优化

1. **PDF 解析升级**：用 `PyMuPDF` 或 `unstructured` 替代 `pypdf`，减少 `\uf070`、`\u0dcd` 等乱码字符
2. **文本归一化**：统一数学字体（γ vs 𝛾），消除评估器误判
3. **Prompt 强化**：明确要求"每个论断必须能在参考资料中找到原句支撑"，抑制幻觉

### 8.2 中期优化

1. **查询改写（Query Rewriting）**：针对 Q20 类语义鸿沟问题，先用 LLM 改写问题为文档用词
2. **增大候选数**：将检索 `n_results` 从 3 调到 5，给短小段落更多入场机会
3. **元数据过滤**：给 chunk 附加"章节"标签，检索时按问题类型限定范围

### 8.3 长期方向

1. **多路检索融合**：BM25 + 向量 + Rerank 三层架构，取长补短
2. **Agent 化**：让 LLM 自主决策"是否需要检索"，避免闲聊类问题浪费 token
3. **持续评估**：将 RAGAS 评估接入 CI/CD，每次代码变更都自动跑一遍

## 九、项目总结

### 9.1 主要成果

| 项目 | 结果 |
|---|---|
| 端到端链路 | ✅ 上传 PDF → 切分 → 向量化 → 提问 → 生成回答 |
| Golden QA | ✅ 20 条 |
| 切分对比实验 | ✅ 9 组配置 |
| 检索方案对比 | ✅ 3 种方案 |
| RAGAS 评估 | ✅ 三指标输出（Faithfulness 0.87 / Precision 0.90 / Recall 1.00） |
| Badcase 归因 | ✅ 7 条 |
| Docker 部署 | ✅ build 成功 |
| FastAPI 服务 | ✅ 接口可用 |
| Agent 工具 | ✅ `search_pdf` 可被自主调用 |

### 9.2 经验总结

1. **评估驱动优化**：没有 RAGAS 的数据，你不知道该优化哪一层。是检索漏召？还是 LLM 幻觉？指标会告诉你。
2. **小语料上简单方案常常够用**：本项目中纯 BM25 优于混合检索、Rerank 无增益，都是"数据集规模小、语义特征弱"导致的。
3. **工程化比模型调优更重要**：Docker、README、实验记录、Badcase 归因，这些才是面试里区分"跑过 tutorial"和"做过项目"的关键。
4. **失败案例比成功案例更有价值**：能解释"为什么加 Rerank 没提升"，比说"我加了 Rerank 提升了 10%"更让人信服。
