# 自适应 RAG 面试追问答案草稿（8 题）

> 本文件为面试准备资料，每题包含：核心答案（可背诵）+ 展开细节（面试官追问时补充）+ 可能的反例（展示深度）。

---

## Q1：你的 RAG 有几种检索路径？怎么决定一条 query 走哪条？

**核心答案**：
有 4 条路径：skip / exact / semantic / hybrid。
决定方式是**基于正则规则的 Query 分类器**（`src/routing/query_classifier.py`），
按关键词模式匹配后分发到不同检索器。

**展开细节**：
- skip：命中闲聊/超范围模式 → 不检索，直接拒答
- exact：命中术语/公式/符号（"五元组"、"γ"、"公式"）→ BM25 关键词检索
- semantic：命中"什么是"、"为什么"、"如何理解" → 向量语义检索
- hybrid：命中"区别"、"步骤"、"对比" → BM25 + 向量 RRF 融合

**为什么不用模型分类**：规则零训练、可解释、迭代快；正则模式可随时调，
上线后如果发现误判，改一行正则就能修。模型虽然泛化好，但需要标注数据、
更新慢、可解释性差。

**反例自省**：规则的缺点是泛化能力弱。如果用户问"折扣因子是干嘛用的"，
没命中"什么是"但语义上属于概念理解类，会被默认归为 semantic，此时反而正确。

## Q2：什么情况下你的系统会拒绝回答？

**核心答案**：
两种情况：
1. **超范围问题**：命中 `OUT_OF_SCOPE_PATTERNS`，如"transformer"、"神经网络"、"天气"等。
2. **检索置信度过低**：检索结果的 `mean_sim < 0.45` 且 `var_sim` 很小，说明没有找到相关内容。

**展开细节**：
- 拒答输出统一为："根据现有知识库，我无法回答这个问题。"
- 拒答决策完全基于检索置信度，不需要额外训练。

**实测数据**：
- 超范围问题（5 条）：拒答准确率 100%
- 正常问题（15 条）：误拒率 0%
- 总准确率 100%

**反例自省**：如果用户问"强化学习的未来趋势"，
这在知识库里可能有相关内容（课件里有"强化学习大模型"章节），
不会拒答；但如果问"特斯拉股价"，则触发超范围拒答。

## Q3：Reranker 在什么条件下反而会降低效果？

**核心答案**：
三种情况会降低效果：
1. **原始检索已正确排序**：Reranker 可能引入新偏差，把本来正确的排序打乱。
2. **短 Query 或专有名词密集**：Reranker 的语义模型对短句的判别力有限。
3. **知识库文档高度相似**：多个 chunk 内容接近时，Reranker 打分差异小，反而引入噪声。

**展开细节**：
- 我的实测中，`always_rerank` 确实提升了 Recall（0.30 → 0.35），但延迟从 2.88ms 涨到 85.2ms，**性价比很低**。
- 条件 Rerank 只在检索一致性低时触发，触发比例 35%，延迟 12.6ms，效果与 always_rerank 相当。

**工程含义**：Reranker 不是银弹，应该"按需触发"。判断是否需要重排的指标是**检索结果的一致性**（方差），而不是盲目全量重排。

**反例自省**：如果我把触发阈值调得太松（loose），大部分 Query 都会触发重排，等同于 always_rerank；如果调得太紧（strict），又会漏掉该重排的场景，导致精度下降。

## Q4：你怎么知道检索失败是 query 理解的问题还是检索器的问题？

**核心答案**：
看**分层归因表**。按 RAGAS 三指标 + Query 分类器的判定结果，把错误分到四层：
- Query 理解：分类器把 Query 分错了路由，或者纯 LLM 无检索
- 检索：分类对，但 `context_recall < 0.6`（完全没找到正确文档）
- 重排：`context_recall ≥ 0.6` 但 `context_precision < 0.6`（找对了但排序差）
- 生成：检索指标正常，但 `faithfulness < 0.6`（资料给了但 LLM 乱答）

**展开细节**：
- 我的实测中，Query 理解层错误率 33.3%，检索层 3.3%，重排和生成层 0%。
- 33.3% 是纯 LLM 方案造成的（无检索能力必然全错），不代表自适应 RAG 的实际表现。
- **真实瓶颈是检索层的 3.3%**，后续优化应聚焦于提升召回率。

**面试加分**：能说出"33.3% 不代表自适应 RAG 的表现"这句话，说明你能区分不同方案导致的差异，而不是简单看总分。

## Q5：多个检索结果矛盾时你怎么处理？

**核心答案**：
用 `conflict_detector` 检测：当多个 chunk 的**语义相似度低于阈值**时，
说明知识库中存在矛盾信息，系统主动提示用户"存在矛盾资料"。

**展开细节**：
- 检测逻辑：对 top-k 检索结果的 embedding 两两计算余弦相似度，如果有一对低于阈值（如 0.5），触发冲突标记。
- 输出时在 answer 前加提示："注意：检索到的资料中存在互相矛盾的信息，请谨慎判断。"

**实测数据**：
- 5 条精心构造的矛盾用例，召回率 80%（4/5）。
- 漏检的 1 条是两个文档用不同措辞表达同一含义，语义相似度未低于阈值。

**改进方向**：
- 用 LLM 二次判定而非纯 embedding 相似度，可提升召回率。
- 但目前 RAG 系统的矛盾检测还是"提示用户"，而不是"自动判断谁对谁错"——因为 RAG 系统没有事实判断能力。

## Q6：Query 分类器用什么实现？规则还是模型？为什么？

**核心答案**：
用**规则（正则）**实现。原因是：
1. **零训练**：不需要标注数据，上线就能用。
2. **可解释**：每条 Query 命中哪条规则，日志里一目了然。
3. **迭代快**：发现误判，改一行正则就修，不用重新训练。
4. **可控制**：业务侧能明确知道"什么样的 Query 走哪条路"，便于调试。

**展开细节**：
- 分类器有 5 种类别（skip / exact / semantic / hybrid / out-of-scope），映射到 4 条路由。
- 每条分类结果附带 `confidence` 和 `reason`，便于日志排查。

**为什么不用模型**：
- 训练需要大量标注数据，我们没有
- 模型推理增加延迟，而 RAG 系统本身已经够慢
- 模型可解释性差，出错时不知道错在哪
- 规则对**领域内固定表达**（如"MDP 五元组"）的判别力已经足够

**反例自省**：规则的缺点是泛化差。如果用户用非常规表达（"那个什么折扣的东西是干嘛的"），可能匹配不到 `"什么是"` 或 `"为什么"`，默认走 semantic，虽然此时结果正确，但逻辑上是巧合。

## Q7：条件 Rerank 的触发条件是什么？阈值怎么定？

**核心答案**：
触发条件是**检索结果的一致性低**：
- 如果 top-k 结果的 embedding 方差 > `variance_threshold`，说明结果分散，可能检索质量差 → 触发重排。
- 如果 top-k 结果的语义一致性 < `consistency_threshold`，说明结果不集中 → 触发重排。

**阈值怎么定**：
我用**3 组阈值扫描**（loose / baseline / strict）对比触发比例和效果：

| 组名 | variance_threshold | consistency_threshold | 触发比例 | Recall@5 | 延迟（ms） |
|---|---|---|---|---|---|
| loose | 0.005 | 0.33 | 65% | 0.35 | 45.2 |
| baseline | 0.01 | 0.66 | 35% | 0.35 | 12.6 |
| strict | 0.02 | 1.0 | 10% | 0.32 | 4.1 |

**选 baseline 的理由**：
- loose 触发太多，等同于 always_rerank，成本高。
- strict 触发太少，Recall 从 0.35 掉到 0.32，效果下降。
- baseline 在效果和延迟间取得最佳平衡：Recall 与 always_rerank 持平（0.35），延迟压到 12.6ms。

**面试加分**：能说出"阈值不是拍脑袋定的，是做了 3 组对比实验扫出来的"，体现工程严谨性。

## Q8：这个项目相比普通 RAG 的差异化在哪？

**核心答案**：
5 个差异化点：
1. **自适应路由**：不是所有 Query 都走向量检索，而是按类型分发到 4 条路径。
2. **条件 Rerank**：不是每次都重排，而是按需触发，节省 85% 延迟。
3. **引用溯源**：每条回答附带 source + chunk_id，可回溯原文。
4. **冲突检测**：多文档矛盾时主动提示，而不是盲信单一检索结果。
5. **自适应拒答**：超范围或低置信度时拒绝作答，避免幻觉。

**更重要的差异化：可量化 + 可解释**
- RAGAS 三指标 + 分层归因表 + 路由轨迹分析
- 所有结论带数字，例如"自适应 RAG 在 Faithfulness 上从 0.9 提升到 1.0"
- 每个错误能追溯到具体层级（Query 理解 / 检索 / 重排 / 生成）

**工程差异化**：
- Docker 一键部署，容器内用 `uv` 自动解析依赖，环境隔离彻底
- `requirements.in` + `requirements.txt` 双层依赖管理
- 完整的实验记录（CSV + MD），每个决策都有数据支撑

**一句话总结**：
普通 RAG 是"检索 + 生成"，我这个是"**自适应检索 + 生成增强 + 可量化评估**"。
