# Week 3 Day 1：Query 分类器 + 检索路由框架设计

## 一、任务回顾

为 RAG 系统加一个"分诊台"：先判断用户问题属于哪一类，再路由到最合适的检索路径，避免"一层打天下"造成的资源浪费或漏召。

## 二、四层路由框架

| 层级 | 名称 | 判定条件 | 路由目标 | 失效条件 |
|---|---|---|---|---|
| L1 | 跳过检索 | 命中闲聊关键词（你好/谢谢/天气/你是谁）| 直接 LLM 回答，不检索 | 用户伪装成闲聊但实际想问知识 → 漏答 |
| L2 | 精确查询 | 含符号/公式/术语/编号信号（γ、P_{sa}、五元组、等式、定义）| 走 BM25 检索 top-3 | 用户用同义表述但无关键词 → BM25 漏召 |
| L3 | 语义查询 | 含概念性提问（什么是/为什么/如何理解/目的）| 走向量检索 top-3 | 术语密集但无关键词信号 → 向量偏 |
| L4 | 混合查询 | 含对比/步骤/综合信号（区别/比较/步骤/哪两种/关系）| BM25 + 向量 RRF 融合 | 单路强命中时被另一路噪音挤占（Day 5 教训）|
| L0 | 超范围拒答 | 命中知识库外主题（Transformer/Q-learning/DQN）| 直接返回"应拒答" | 主题词未覆盖时漏判 |

## 三、分类器实现

- **位置**：`src/routing/query_classifier.py`
- **方法**：规则层（正则 + 关键词）
- **输出**：`ClassificationResult(query, query_type, confidence, reason)`
- **优先级顺序**：skip → out-of-scope → hybrid → semantic → exact → 默认 semantic

**规则清单**：

| 类型 | 典型正则 |
|---|---|
| skip | `^你好` / `^hi\b` / `天气` / `你能做什么` |
| out-of-scope | `transformer` / `q-?learning` / `dqn` / `神经网络` |
| hybrid | `区别` / `比较` / `步骤` / `哪两种` / `关系` / `描述` |
| semantic | `什么是` / `为什么` / `如何理解` / `目的是什么` |
| exact | `[A-Z]\^?\*?` / `γ\|β\|α\|π` / `五元组` / `等式` / `定义` |

## 四、评估结果

- **测试集**：`data/golden_qa/qa_extended.json`（25 条）
- **准确率**：**96.00%**（24/25）
- **错误案例数**：1 条

### 错误案例（1 条，作为边界样本保留）

**Q**：最优价值函数 V*(s) 和最优策略 π*(s) 的关系是什么？
**期望**：exact　**预测**：hybrid　**原因**：命中 hybrid 模式 `r"关系"`

**为什么保留不修**：
这条问题**既是 exact（含具体符号 V*、π*）又是 hybrid（问两者的关系）**，人工标注都可能给出不同答案。这正是规则分类器的天然局限，作为日志证据比强行修复更有价值。

### 调参过程（记录迭代）

| 版本 | 调整 | 准确率 |
|---|---|---|
| v1 | 初始规则 | 88%（22/25）|
| v2 | 加 `r"过程"` 到 hybrid | 84%（21/25）↓ |
| v3 | 删 `r"过程"`，加 `r"什么是"` 到 semantic，删 `r"是什么"` 从 exact | 92%（23/25）|
| v4 | 修正标注："什么是占用度量"应为 semantic 而非 exact | **96%（24/25）** |

**关键教训**：规则越宽泛 → 误命中越多；规则越精确 → 漏命中越多。这和 Day 5 的检索评估（Precision/Recall 权衡）本质一致。

## 五、决策记录（5 条）

### 决策 1：为什么分四层（含超范围共五类）？

四层分别对应四类真实场景：闲聊（不需检索）、术语（关键词强）、概念（语义强）、综合（需多片段）。一层打天下会导致两种问题：(1) 闲聊也走检索，浪费 token；(2) 综合问题 top-3 只找到一半资料，答案不完整。

**图书馆类比**：不是所有问题都要查书。读者打招呼 → 直接回应；问术语 → 查索引；问概念 → 翻章节；问对比 → 综合多处。

### 决策 2：规则 vs embedding 分类？

Day 1 选规则，理由三条：
1. **零延迟**：正则匹配毫秒级，embedding 要加载模型
2. **可解释**：命中哪条规则一目了然，方便 debug
3. **先立 baseline**：未来上 embedding 有对比基准

**代价**：规则无法处理语义歧义（如"V* 和 π* 的关系"），准确率上限约 95%。

### 决策 3：路由粒度为什么是"四层"而不是"两类"？

"检索/不检索"二分太粗。检索内部还要分 BM25/向量/混合，因为 Day 5 已实测三种检索器表现差异明显：
- 纯向量：Recall@5 = 0.80
- 纯 BM25：Recall@5 = 0.85
- 混合：Recall@5 = 0.85，MRR 0.825

既然有区分度，就值得分层。

### 决策 4：失效条件为什么必须写？

工程里最怕的不是"不工作"，是"看起来在工作其实错了"。提前写清失效边界，将来出错时能快速定位。

**每层的失效场景举例**：
- L1 skip 误判：用户用闲聊语气提知识问题 → 应加"是否包含领域关键词"二次校验
- L2 exact 漏召：用户用同义表述 → 应加同义词扩展
- L4 hybrid 噪音挤占：Day 5 的 Q5 案例（向量排 0、BM25 排 1，融合后排第 2）

### 决策 5：超范围题的用途？

5 条超范围题（Transformer/Q-learning/DQN 等）用于测试系统"该拒答时能否拒答"。大部分 RAG 项目只测"能答对多少"，不测"该拒答时会不会硬答"。加入拒答评估，能证明系统的**边界感知能力**，是面试加分项。

### 决策 6：为什么不加"数量类（count）"规则？

独立挑战阶段评估了"新增 count 类"的可行性，**决定不加**，理由三条：

1. **数据驱动**：当前 `qa_extended.json` 25 条里**没有一条** count 类问题（"有几个/几种/几条"），加了规则也无从评估。
2. **规则冲突**：count 类问题通常含"哪几种/哪两种"，和 hybrid 的信号词**高度重叠**。若加 count 规则，必须决定它的优先级在 hybrid 之前还是之后，引入不必要的复杂度。
3. **收益不明**：即便加了，也没有测试数据能证明它有效。规则越少越好，能不加就不加。

**这体现了工程上的一个原则**：**不为假想的场景写代码**。加规则之前先问"数据里有没有、加了能不能评估、会不会和现有规则冲突"。

### 决策 7：未来分类器的演进路径

当前规则分类器准确率 96%，**上限约 95%**，剩余错误都是"语义歧义"（如"V* 和 π* 的关系"）。后续演进路径：

1. **短期**：扩大 out-of-scope 关键词覆盖面（已完成的一部分）
2. **中期**：引入 embedding 分类器，把问题转向量后跟几类模板比相似度
3. **长期**：引入 LLM 分类器（用 Qwen 直接分类），准确率可达 98%+，但每次多一次 API 调用
4. **工程落地**：规则 + LLM 双轨——规则先快速判，置信度低或未命中时交给 LLM 兜底

**这也回答了"为什么还要学规则分类器"**：规则不是要被替代，而是要作为 fallback 和 baseline 长期存在。
