# Week 4 Day 1 实验日志：结构化对话状态设计 + 多轮测试集构建

## 1. 任务目标
设计结构化对话状态对象，定义状态转换规则，构建 20 条多轮对话测试集，实现话题切换检测。

## 2. 核心产出
- `src/conversation/state.py`：Pydantic 状态对象
- `data/golden_qa/multi_turn_test.json`：20 条多轮测试集
- `experiments/week4_day1_log.md`：本实验日志

## 3. 状态对象设计
| 字段名 | 数据类型 | 更新条件 |
|---|---|---|
| `current_entities` | `List[str]` | 话题切换时替换，否则追加（去重） |
| `confirmed_info` | `Dict[str, str]` | 用户明确确认或系统无歧义抽取时写入 |
| `pending_questions` | `List[str]` | 发现信息缺口时加入，用户回答后移除 |
| `topic_switch_flag` | `bool` | 实体重叠度 < 阈值（0.3）时置为 True |
| `history_summary` | `str` | 每轮结束后更新，压缩历史关键信息 |

## 4. 状态转换规则
- 更新实体：`topic_switch` 为 True 时替换，为 False 时追加去重。
- 触发话题切换：改写后 query 与当前 query 的实体重叠度（Jaccard 相似度）低于阈值（0.3）。
- 重置状态：用户显式要求（“重新开始”等），或隐式触发（超20轮/超时）。

## 5. 决策记录
### 决策记录 1：为什么用结构化状态对象而非简单消息列表？
**背景：** 多轮对话中，最简单的做法是把所有历史消息拼成一个列表（List[Message]）喂给检索。
**决策：** 采用 Pydantic 定义的结构化状态对象（ConversationState）来管理对话上下文。
**原因：** 消息列表把所有历史同等对待，导致“用户已经从手机切到电脑了，检索 query 还在用手机的上下文”。结构化状态对象把“当前意图”和“历史上下文”分离，检索只走前者（current_entities）。
**影响：** 提升了多轮检索的准确率，避免了旧话题对当前话题的污染。

### 决策记录 2：为什么是这 5 个字段？
**背景：** 定义状态对象时，字段太少无法覆盖多轮场景，字段太多会让代码变得臃肿难以维护。
**决策：** 选定 `current_entities`、`confirmed_info`、`pending_questions`、`topic_switch_flag`、`history_summary` 这 5 个字段。
**原因：** 参考 GSC-QA 框架的目标追踪模块-17。这 5 个字段刚好覆盖多轮对话的完整生命周期：当前讨论实体（意图追踪）、已确认信息（事实沉淀）、待澄清问题（信息缺口）、话题切换标记（状态流转）、历史轮次摘要（长记忆压缩）。缺一不可。
**影响：** 既保证了检索时能拿到核心意图，又控制了上下文长度，避免 Token 爆炸。

### 决策记录 3：话题切换阈值怎么定？
**背景：** 需要一个量化标准来判定用户是否切换了话题，不能靠主观感觉。
**决策：** 使用改写后 query 与当前 query 的实体重叠度（Jaccard 相似度），阈值定为 **0.3**。
**原因：** 参考京东面试官认可的方案：改写后 query 与当前 query 的实体重叠度低于阈值时，降级为只用当前 query 检索。如果阈值定太高（如0.8），用户补充“拍照好”会被误判为切换；如果定太低（如0.1），用户说“换个话题，电脑呢”就会被漏判，导致旧上下文污染检索。0.3 是兼顾灵敏度和准确度的经验值。
**影响：** 低于 0.3 时，`topic_switch_flag` 置为 `True`，并触发实体替换逻辑。

### 决策记录 4：状态重置的触发条件？
**背景：** 状态对象不能无限增长，也不能让上一个用户的记忆污染下一个用户。
**决策：** 遇到以下情况，直接返回一个全新的 `ConversationState()`：
1. **显式重置**：用户主动说“重新开始”、“算了不聊了”等。
2. **隐式重置**：对话轮次超过 20 轮，或者系统长时间无响应导致会话超时。
**原因：** 显式重置是对用户意图的尊重；隐式重置是防止长期记忆堆积导致的模型幻觉和性能下降。
**影响：** 保证了状态对象的生命周期清晰，避免“串台”事故。
