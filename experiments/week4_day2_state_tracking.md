# Week 4 Day 2: 状态追踪与长期记忆管理实验报告

## 1. 实验目的
验证在长对话（20轮）场景下，引入“结构化状态对象（State）+ 滑动窗口 + 摘要压缩”相比于“无状态全量历史”，在 Token 消耗和状态持久化上的差异。

## 2. 实验设置
- **测试集**：20 轮酒店预订场景对话（包含预算、时间、过敏源、发票、宠物等关键实体）。
- **对照组（无状态管理）**：不注入状态卡片，使用 `trim_messages` 保留 2000 Token 预算的完整历史。
- **实验组（有状态管理）**：每轮使用 LLM 提取并持久化 `ConversationState`，历史窗口压缩至 300 Token，并降维注入 `confirmed_info` 及历史摘要。

## 3. 核心量化指标结果

| 测试指标 | 对照组 (无状态) | 实验组 (有状态) | 实验结果 (达标线) | 结论 |
| :--- | :--- | :--- | :--- | :--- |
| **总 Token 消耗** | 17,854 | 9,702 | **节省 45.66%** (≥30%) | ✅ 通过 |
| **状态恢复成功率** | 无此机制 | 100% | **100%** (100%) | ✅ 通过 |
| **关键实体保留率** | (易被截断遗忘) | 100% (存JSON) | **100%** (≥90%) | ✅ 通过 |

## 4. 多用户并发隔离测试
- 通过 `session_id` 分别创建 `user_A` 和 `user_B` 的独立 JSON 文件及内存 History 字典。
- **测试结果**：A 用户询问“我刚才要订哪里的酒店”时，准确回答“北京”，未受 B 用户“上海”信息干扰。多租户隔离成功率 100%。

## 5. 结论与优化总结
- **结论**：结构化状态管理能极大幅度降低上下文 Token 占用，且能保证核心事实永不丢失。
- **避坑经验**：
  1. 必须对大模型返回的 JSON 进行防御性清洗（防嵌套字典）。
  2. 摘要文本不能无限膨胀，必须硬截断（如 `[-300:]`）。
  3. 注入状态时采用“降维注入”，只注入 `confirmed_info` 和摘要，舍弃庞大的 `pending_questions` 列表。
