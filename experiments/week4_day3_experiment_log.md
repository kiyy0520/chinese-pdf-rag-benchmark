## 一、 核心指标统计（基于 20 条多轮对话测试集）
- **总测试集规模**：20 条。
- **Rewrite 平均精确率**：96.6%（目标 ≥ 80%） -> *注：受简单字符串匹配局限，部分过度改写未完全惩罚。*
- **Rewrite 平均召回率**：79.2%（目标 ≥ 85%） -> *注：多项改写不足（如漏掉限定词）拉低了分数。*
- **规则降级触发比例**：95%（19/20 触发）。 -> *注：暴露出字符交集算法的严重误杀问题。*

## 二、 失效模式分析记录（必选）
| 失效类型 | 表现 | 根因 | 应对与降级策略 |
| :--- | :--- | :--- | :--- |
| **过度改写** | 引入了上下文中不相关的实体（如把两个耳机都塞进去） | LLM 过度推断 | 实体重叠度检查：如果新实体太多则降级。 |
| **改写不足** | 遗漏了当前问句的关键限定词（如漏了“黑色”）或历史实体（如漏了“深圳”） | 指代链过长 / LLM 偷懒 | 回溯多轮历史，或采用 LLM 语义判断。 |
| **话题误判** | 用户已切换话题（问退货），改写仍强行带上旧上下文（如带上 AirPro 耳机） | 缺少话题切换检测 | 话题切换阈值触发，或依靠 LLM 语义评估。 |
| **降级误杀** | **原本改写完美的 Query，被死板的规则系统强制退回原句。** | 字面重叠度低，未能识别代词与实体的关联 | 引入大模型裁判（LLM Judge）替代纯规则。 |

## 四、 前沿工程化探索：LLM as a Judge 实验
在完成基础的规则降级后，我们引入了真实大模型（DeepSeek-V4.1-Flash）作为裁判进行降级判断。
- **实验发现**：当仅将【当前问句】和【改写结果】输入给 LLM Judge 时，由于**缺少历史上下文**，LLM 会非常谨慎地判定 `case_02`（“这个”变“AirPro”）为 `False` 并触发降级（因为它不知道历史聊了啥）。
- **工程启示**：
  1. **混合降级机制（Hybrid）**：先用规则（如字符重叠、向量相似度）快速过滤明显错误，对于模糊地带再调用 LLM Judge，兼顾成本与准确率。
  2. **LLM 调用的确定性**：评估判定类任务必须设置 `temperature=0.0`，避免大模型发散；必须使用 `response_format={"type": "json_object"}` 保证程序能稳定解析。
  3. **上下文完备性**：做语义 Judge 时，必须把 `history` 也塞进 Prompt 中，否则会导致严重的误杀。
